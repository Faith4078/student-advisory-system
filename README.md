# Thesisly — Student Project Repository and AI Advisory System

A web application that gives a faculty of computing a searchable home for
student final-year and SIWES project reports, plus an AI Academic Advisor
that is grounded in that repository's actual content rather than general
knowledge. Built with TanStack Start, Drizzle ORM, PostgreSQL (Neon) with
`pgvector`, Better Auth, Google Gemini, and Jina AI.

## What This Is

Final-year and SIWES project reports in a faculty of computing typically
disappear into a supervisor's folder once graded. There is no searchable
record of prior work, and existing AI advising tools know nothing about a
specific department's own project archive. This system solves both
problems at once:

- A **repository**: students upload their project report as a PDF; the
  system reads it, extracts structured fields, and keeps the full
  verbatim text so it can be searched and quoted precisely later.
- **Hybrid search**: finds relevant projects by both exact keywords and
  meaning, not either alone.
- An **AI Academic Advisor**: a conversational, tool-calling agent that
  looks up real repository evidence before answering, and whose citations
  are resolved server side from what it actually retrieved, so it cannot
  claim evidence it never looked up.

## Key Features

- **PDF ingestion and extraction.** Upload a PDF; Gemini reads it and
  extracts structured fields (title, author, department, methodology,
  results, conclusion, etc.), plus the complete verbatim text. A single
  uploaded document can contain several distinct student projects bound
  together (common for SIWES/internship reports); each is detected and
  kept separately, with its own page range within the shared source file.
- **Late-chunked, full-text semantic search.** The full report text is
  split into passages and embedded using late chunking, so each passage's
  embedding still reflects the context of the whole document it came
  from, not just its own isolated sentence.
- **Hybrid retrieval with Reciprocal Rank Fusion (RRF).** Project search
  runs lexical (PostgreSQL full-text), semantic (`pgvector` cosine
  similarity), and fuzzy-title (`pg_trgm`) candidate retrieval in
  parallel, merges the three ranked lists by position (not raw score)
  using RRF, then re-scores the top slice with a neural cross-encoder
  reranker (`jina-reranker-v2-base-multilingual`) for the final order.
- **An AI Advisor with eight tools**, not a single fixed prompt: six
  read-only catalogue tools (`search_projects`, `get_project`,
  `search_project_chunks`, `get_source_document`, `get_project_links`,
  `get_project_statistics`) and two student-memory tools
  (`remember_about_student`, `forget_about_student`). The model decides,
  per question, which tools to call and how many times.
- **Server-resolved citations.** The citation list shown beneath an
  Advisor reply is assembled by the application's own code from the tool
  calls that turn actually made, never generated by the model describing
  its own sources. A fresh tool call is required even for a project
  discussed earlier in the same conversation, so prior prose is never
  treated as if it were still-valid grounding.
- **In-chat cited-page viewer.** A student can open the exact PDF page an
  Advisor citation came from, directly inside the conversation, without a
  separate full-document viewer unless the project's author has opted in.
- **Author-controlled downloads.** Each project owner independently
  chooses whether their full report PDF may be downloaded by other
  students; viewing a cited page is always possible regardless, since it
  is the same content a citation already shows.
- **Confirm-before-save memory.** If a student explicitly asks the
  Advisor to remember something, it saves it immediately. If a student
  merely mentions a preference in passing, the Advisor asks for
  confirmation first rather than saving it silently, and can delete a
  remembered fact on request.
- **Security guardrails.** Arcjet protects both HTTP routes (rate
  limiting, sensitive-information detection) and the Advisor's own tool
  calls (prompt-injection detection on user input and on tool-retrieved
  content, a token-bucket rate limit on tool calls).
- **Cache-aside read path.** Search rankings and Advisor tool results are
  cached (Upstash Redis) by a hash of their own inputs; a cache outage
  degrades gracefully to live computation rather than breaking the app.

## Architecture

```
PDF upload -> Gemini extraction -> structured fields + full verbatim text
                                         |
                                         v
                          late-chunked embeddings (Jina) -> pgvector
                                         |
   student query -> lexical (Postgres FTS) ----+
                  -> semantic (pgvector)  ------+--> RRF fusion -> neural
                  -> fuzzy title (pg_trgm)------+    reranker -> results

   student <-> AI Advisor (Gemini, function-calling)
                  |-- search_projects / get_project / search_project_chunks
                  |-- get_source_document / get_project_links / get_project_statistics
                  |-- remember_about_student / forget_about_student
                  -> citations resolved server side from actual tool calls
```

Three layers, each documented in more depth in `docs/methodology-explainer.tex`:

1. **Repository layer** — `ingestion.server.ts`, `gemini.server.ts`,
   `chunking.server.ts`, `pdf-text.server.ts`, `embedding-index.server.ts`.
   Turns an uploaded PDF into structured fields, full verbatim text, and
   page-accurate, late-chunked embeddings.
2. **Retrieval layer** — `projects.server.ts`, `jina.server.ts`.
   Hybrid lexical/semantic/fuzzy candidate retrieval, RRF fusion, neural
   reranking, and cache-aside ranking.
3. **Advisor layer** — `advisor-agent.server.ts`, `advisor.server.ts`,
   `mem0.ts`. The Gemini tool-calling agent loop, server-resolved
   citations, and student-memory tools.

## Database Schema

All tables are defined in `src/db/schema.ts` and migrated with Drizzle.

| Table | Purpose |
|---|---|
| `user`, `session`, `account`, `verification` | Better Auth's own tables |
| `recovery_credential` | Backup sign-in recovery codes |
| `project` | A single project record: structured fields, full verbatim text, status (draft/ready_to_publish/published/archived), source document link and page range, author-controlled `allow_download` flag, lexical search vector |
| `project_chunk` | Late-chunked passages of a project's full text (or structured fields for manually entered projects), each with its own embedding, section title, and page number |
| `project_link` | A project's external links (GitHub, live demo, etc.) |
| `document` | An uploaded PDF's metadata and R2 storage key (one document can back several projects) |
| `ingestion_job` | Tracks the status of one extraction run against an uploaded document |
| `advisor_conversation`, `advisor_message` | Chat history, including each message's resolved citations |

## Getting Started

1. Copy `.env.local.example` to `.env` and fill in the values described
   below.
2. Install dependencies and apply the database migrations.
3. Start the development server.

```bash
pnpm install
pnpm db:migrate
pnpm dev
```

The app runs at `http://localhost:3000` (or the next free port if 3000 is
already in use).

### Environment Variables

| Variable | Required | Purpose |
|---|---|---|
| `BETTER_AUTH_SECRET` | Yes | At least 32 random characters, used to sign sessions |
| `BETTER_AUTH_URL` | Yes | Base URL the app is served from |
| `DATABASE_URL` | Yes | PostgreSQL connection string (Neon recommended, for `pgvector`) |
| `DATABASE_URL_POOLED` | No | A pooled connection string, if your provider supplies one |
| `GEMINI_API_KEY` | Yes, for ingestion and the Advisor | Google Gemini API key |
| `GEMINI_MODEL` | No | Overrides the default model (`gemini-3.8-flash`) |
| `JINA_API_KEY` | Yes, for search and embeddings | Jina AI API key (embeddings and reranker) |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | No | Enables result caching; the app falls back to live computation without it |
| `ARCJET_KEY` | No | Enables rate limiting and prompt-injection/content guards; features fail open (allowed) without it |
| `MEM0_API_KEY` | No | Enables the Advisor's cross-conversation student memory; the app works without it, with memory disabled |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME` | Yes, for PDF upload | Cloudflare R2 (S3-compatible) storage for uploaded source PDFs |

Every external service beyond the database and auth secret is designed to
degrade gracefully, not crash the app, when its key is left unset.

### Authentication

Students sign in with their real school email as the Better Auth identity
and a matric number (format `CSC/2019/061`) as the sign-in username. When
the Better Auth configuration itself changes, regenerate its Drizzle
schema and create a migration:

```bash
pnpm auth:generate
pnpm db:generate
```

## The AI Advisor's Tools

The Advisor is a Gemini function-calling agent, not a single fixed
prompt; it decides per question which of these to call, and how many
times, before answering:

**Catalogue tools (read-only, published data only):**

1. `search_projects` — hybrid search over the catalogue, for finding
   which projects match a topic, technology, or department.
2. `get_project` — full structured detail for one known project.
3. `search_project_chunks` — semantic search directly over complete
   verbatim report text, for specific questions a short summary field
   cannot answer.
4. `get_source_document` — metadata about a project's source PDF (file
   name, page count, upload date).
5. `get_project_links` — a project's external links.
6. `get_project_statistics` — catalogue-wide counts by department,
   project type, and year.

**Student-memory tools:**

7. `remember_about_student` — saves a fact about the current student for
   future conversations. Called immediately only when the student
   explicitly asks to be remembered; otherwise the Advisor asks for
   confirmation first.
8. `forget_about_student` — deletes a previously remembered fact matching
   a description, whenever the student asks.

Every citation shown to a student is built by the application's own code
from the tool calls a turn actually made, never generated by the model
describing its own sources.

Integration tests under `src/lib/*.test.ts` deliberately talk to the real

## Security

- Arcjet rate-limits and screens both ordinary HTTP routes
  (`security.server.ts`) and the Advisor's own tool-call loop
  (`advisor-agent.server.ts`): user-authored text is screened in
  `block` mode, while content a tool retrieved from the application's own
  database is screened in a softer `audit` mode, since retrieved academic
  text was observed to trigger false positives when hard-blocked.
- Uploaded PDFs are stored in a private Cloudflare R2 bucket; the
  application never exposes a storage key, a public bucket URL, or the
  raw file bytes directly to the client. The in-chat page viewer renders
  individual pages to PNG server side; the full-document route serves
  the original PDF only for inline viewing by default, with downloading
  gated behind the project author's own `allow_download` setting.
- Passwords and sessions are handled entirely by Better Auth, not a
  hand-rolled implementation.

## Deployment

This project uses Nitro as its server adapter, so it can run on any
Node-compatible host:

```bash
pnpm build
node dist/server/index.mjs
```

The build output is a self-contained Node server. Push the `dist/`
directory to your host and run the command above. For host-specific
presets (Vercel, Netlify, Cloudflare, AWS Lambda, etc.), see
[the Nitro deployment docs](https://v3.nitro.build/deploy).
